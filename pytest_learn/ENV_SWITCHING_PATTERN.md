# Паттерн переключения окружений (dev/test/prod)

> Выучен из реальной боевой инфры (`vat/supplier.admin`, Yii2/PHP, GitLab CI) и перенесён на Python.
> Это не framework-специфичная штука — работает НИЖЕ любого фреймворка, на уровне процесса ОС.

## Суть паттерна (язык/фреймворк не важен)

1. Переменная окружения (`APP_ENV` и т.п.) выставляется СНАРУЖИ процесса — через shell (`export`),
   CI-переменную, Docker `environment:` — ДО того как Python вообще начал импортировать твой код.
2. Код загрузки конфига (ОДИН, общий для прода и тестов) ЧИТАЕТ эту переменную и решает, какой
   `.env`-файл (или слой файлов) подгрузить.
3. Что РЕШАЕТ окружение — не аргумент внутри приложения, а то, КАК/С ЧЕМ ты его запустил снаружи.

В PHP-оригинале (`vat/supplier.admin`) это выглядело так:
```php
// yii_test — отдельный launcher для тестов
defined('YII_ENV') or define('YII_ENV', 'test');   // флаг ставится СНАРУЖИ, до общего кода
require __DIR__ . '/env.php';

// env.php — ОБЩИЙ для yii и yii_test
if (YII_ENV === 'test') {
    // грузит test.env СВЕРХУ обычного .env
}
```
Два разных launcher-скрипта (`yii` / `yii_test`), ОДИН общий конфиг-загрузчик, который ветвится
по заранее выставленному флагу.

## Почему это работает НЕЗАВИСИМО от фреймворка

`os.environ` — глобальный для ВСЕГО процесса Python, выставляется ДО того как интерпретатор начал
читать твои файлы. Любой конфиг-загрузчик (`pydantic-settings`, `os.getenv`, Django `settings.py`,
Flask `app.config`) читает из ОДНОГО И ТОГО ЖЕ места. Фреймворк не видит и не управляет ЭТИМ слоем —
он работает НИЖЕ него. Поэтому паттерн ложится на FastAPI, Flask, Django, aiogram, голый скрипт —
куда угодно. Разница между фреймворками — только КОГДА каждый из них РЕАЛЬНО читает конфиг:

- **FastAPI** (с `pydantic-settings`) — обычно читаешь конфиг САМ, когда хочешь (часто лениво, через
  `Depends(get_settings)` + `lru_cache`) — больше контроля, легче тестировать (можно подменить
  зависимость в тестах вообще без env-переменных, через `app.dependency_overrides`).
- **Django** — `settings.py` читается при старте (`django.setup()`) — похоже на PHP-кейс, конфиг
  грузится РАНО и один раз, жёстче по времени.
- **Flask** — `app.config.from_object(...)`/`from_envvar(...)` — вызываешь явно сам, полный контроль.
- **aiogram** — НЕ исключение из ЭТОГО паттерна (его "сложность" вчера была про ДРУГУЮ вещь —
  `contextvars`/`Bot.get_current()`, не про переключение env). Для своих `env.read_env()` в
  `main.py` аiogram ничем не отличается от любого другого Python-кода.

## Конкретный рецепт для FastAPI (`pydantic-settings`)

```python
# config.py
import os
from functools import lru_cache
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    database_url: str
    model_config = SettingsConfigDict(extra="ignore")

def get_env_name() -> str:
    return os.getenv("APP_ENV", "local")          # дефолт — обычная разработка

@lru_cache
def get_settings() -> Settings:
    env = get_env_name()
    return Settings(_env_file=f".env.{env}")       # .env.local / .env.test / .env.prod
```

Запуск:
```bash
uvicorn main:app                     # APP_ENV не задан → .env.local
APP_ENV=test pytest                  # .env.test — ДО старта python, через shell/CI
```

## Главный капкан — ПОРЯДОК

Переменную `APP_ENV` нужно выставить ДО того, как Python начнёт импортировать модуль, который
читает конфиг на уровне модуля (как `engine = create_async_engine(...)` в `mem_hunter/src/db/session.py` —
выполняется СРАЗУ при импорте, не при вызове функции).

**Правильно** — задать переменную СНАРУЖИ процесса, аналог отдельного PHP-launcher'а (`yii_test`):
```bash
APP_ENV=test pytest   # переменная в окружении ДО того как python вообще запустился
```

**Рискованно** — выставлять `os.environ["APP_ENV"] = "test"` ВНУТРИ `conftest.py` ПОСЛЕ того, как
где-то выше уже случился `import` модуля с конфигом на уровне модуля — тогда он успеет прочитать
СТАРОЕ/дефолтное значение до того, как ты его переопределил. Если делаешь так — переменная должна
стоять строкой НОМЕР ОДИН в `conftest.py`, раньше любых `from app import ...`.

## ПОПРАВКА после разведки на GitHub (реальные FastAPI-проекты)

Проверил `tiangolo/full-stack-fastapi-template` (эталонный проект автора FastAPI) и разбор тестовых
паттернов в реальных проектах — картина чуть другая для FastAPI конкретно:

- **Официальный шаблон** — ОДИН `.env`-файл + поле `ENVIRONMENT: Literal["local","staging","production"]`,
  используется НЕ для выбора файла, а для СТРОГОСТИ валидации (дефолтные секреты → warning в деве,
  error в проде). Какое окружение активно — решает ИНФРА (Docker/деплой), не ветвление в коде на
  несколько `.env.{env}` файлов.
- **Для тестов — доминирующий паттерн — `app.dependency_overrides`**, НЕ env-файлы:
  ```python
  app.dependency_overrides[get_db] = lambda: test_session
  ```
  Это точечная подмена ОДНОЙ зависимости (`Depends(get_db)`) на тестовую версию прямо в Python-коде.
  Работает ТОЛЬКО благодаря DI-системе FastAPI (`Depends(...)`) — у PHP/Yii такого механизма нет,
  поэтому там и родился паттерн с multi-env-файлами через launcher-скрипты.

**Вывод:** оба паттерна РЕАЛЬНЫ и живут рядом, просто под разные задачи:
- env-файл + `ENVIRONMENT`-флаг (из PHP-паттерна выше) — для ОБЩЕГО конфига (секреты, debug, логи).
- `dependency_overrides` — для ТОЧЕЧНОЙ подмены БД/внешних сервисов именно в тестах, без файлов вообще.

Для `todo_api.py` это значит: вместо (или в дополнение к) `APP_ENV`-переменной, для теста БД
естественнее будет `app.dependency_overrides[get_db] = ...` — ближе к тому, как делают "нормальные"
FastAPI-проекты.
