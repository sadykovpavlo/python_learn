# Mock — шпаргалка (методы и атрибуты, которые IDE НЕ подсказывает)

## Почему IDE их не подтягивает
`MagicMock` создаёт методы/атрибуты **динамически в рантайме** (при обращении).
Статический анализатор не знает заранее, что у объекта есть `.assert_called_once_with`,
поэтому нет автокомплита, а иногда ещё и warning "unresolved attribute". Это нормально —
методы реально существуют, просто появляются во время выполнения. Значит их надо помнить.

Дальше `m` — это мок: `m = mocker.patch("module.func")`.

---

## 1. Проверки ВЫЗОВА (assert_*) — их пишут в конце теста
| метод | что проверяет |
|---|---|
| `m.assert_called()` | вызван хотя бы раз |
| `m.assert_called_once()` | вызван РОВНО один раз (аргументы не важны) |
| `m.assert_called_with(a, b, key=1)` | ПОСЛЕДНИЙ вызов был именно с такими аргументами |
| `m.assert_called_once_with(a, b)` | вызван один раз И с такими аргументами (2-в-1, самый ходовой) |
| `m.assert_any_call(a)` | среди всех вызовов был хотя бы один с такими аргументами |
| `m.assert_has_calls([call(1), call(2)])` | были эти вызовы именно в таком порядке |
| `m.assert_not_called()` | не вызывался ни разу |

`call` для `assert_has_calls` импортируется: `from unittest.mock import call`.

---

## 2. Атрибуты для ИНСПЕКЦИИ (читаешь, чтобы сделать обычный assert)
| атрибут | что содержит |
|---|---|
| `m.called` | bool — вызывали ли |
| `m.call_count` | int — сколько раз |
| `m.call_args` | аргументы ПОСЛЕДНЕГО вызова (объект `call`); `m.call_args.args`, `m.call_args.kwargs` |
| `m.call_args_list` | список ВСЕХ вызовов (список `call`-объектов) |

Пример «ручной» проверки, когда assert_* не хватает гибкости:
```python
assert m.call_count == 2
assert m.call_args.args[0] == 42          # первый позиционный арг последнего вызова
```

## 3. Настройка ОТВЕТА мока (задаёшь ДО вызова, в patch или после)
| приём | эффект |
|---|---|
| `mocker.patch("mod.f", return_value=X)` | всегда возвращает `X` |
| `mocker.patch("mod.f", side_effect=SomeError)` | при вызове КИДАЕТ исключение |
| `mocker.patch("mod.f", side_effect=[1, 2, 3])` | по очереди 1, потом 2, потом 3 |
| `mocker.patch("mod.f", side_effect=lambda x: x*2)` | ответ вычисляется функцией от аргументов |
| `m.return_value = X` | то же, но задать после создания мока |
| `m.side_effect = ...` | то же для side_effect |

Правило: `return_value` — ЧТО вернуть; `side_effect` — КАК себя вести (исключение/последовательность/логика).
Без `return_value` мок возвращает новый пустой MagicMock (его repr выглядит как "случайное число" — это id объекта).

## 4. Инструменты pytest-mock (fixture `mocker`)
| приём | зачем |
|---|---|
| `mocker.patch("mod.func")` | подменить функцию/атрибут по пути (патчь ТАМ, где используется!) |
| `mocker.patch.object(obj, "method")` | подменить метод у конкретного объекта/класса |
| `mocker.Mock()` / `mocker.MagicMock()` | создать мок-объект вручную (напр. фейковый клиент) |
| `mocker.spy(obj, "method")` | ОБЁРТКА: реальный метод работает, но вызовы записываются (можно assert_*) |
| `mocker.stub(name="cb")` | простой мок-заглушка (напр. для колбэка) |
| `mocker.patch(..., autospec=True)` | мок повторяет сигнатуру оригинала → ловит вызовы с неверными аргументами |

Плюс `mocker` сам откатывает все патчи после теста — вручную ничего чистить не надо.

---

## Мини-приоритет для собеса (выучить в первую очередь)
1. `return_value=` / `side_effect=`  — задать ответ/поведение
2. `assert_called_once_with(...)`     — 90% проверок взаимодействия
3. `assert_not_called()`              — доказать, что ветка НЕ дёрнула сервис
4. `call_count` / `call_args`         — когда нужна гибкая проверка
5. `mocker.patch.object` и `autospec` — на «плюс к senior»
